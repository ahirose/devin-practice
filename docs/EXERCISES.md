# 週別 演習ガイド（コピペ用プロンプト付き）

各演習は「① 目的 → ② Devinに渡すプロンプト → ③ 自分での検証コマンド → ④ 学びのポイント」で構成しています。
プロンプトはそのままコピーして、Devinのセッション（Web / Slack / IDE / CLI）に貼り付けてください。

---

## Week 1: 基礎とセッションの回し方

### 1-1. コードベースQ&A（コード変更なし）
プロンプト:
```
このリポジトリ（devin-practice）の構成と処理の流れを説明してください。
- taskman add コマンドを実行したとき、どのファイルのどの関数がどの順で呼ばれるか
- タスクがどこに永続化されるか
コードを引用しながら説明してください。コードは変更しないでください。
```
検証: 説明中のファイル・関数名が実際に存在するか自分で確認する。
学び: Devinはまず読ませる。PRを作らせないタスクも有効。

### 1-2. 低リスクな変更でPRの流れを体験
プロンプト:
```
README.md に「トラブルシューティング」セクションを追加してください。
含める内容:
1. `taskman: command not found` の場合の対処（venvの有効化 / pip install -e ".[dev]"）
2. `ModuleNotFoundError: taskman` の場合の対処（PYTHONPATH=src での実行方法）
コードは変更せず、README.mdのみ編集してPRを作成してください。
```
検証: `git diff` がREADMEのみであること。
学び: 「触ってよい範囲」を明示するとスコープが逸れない。

### 1-3. テスト追加（完了条件が明確なタスク）
プロンプト:
```
tests/test_service.py に TaskService.search() のユニットテストを追加してください。
条件:
- 既存のテストとフィクスチャ（service）のスタイルに合わせる
- タイトル一致・タグ一致・該当なしの3ケースを含める
完了条件: `pytest -q` が全件パスし、`ruff check .` がクリーンであること。
プロダクションコード（src/）は変更しないでください。
```
検証: `pytest -q && ruff check .`
学び: 完了条件（テストがグリーン）を書くとDevinが自己検証する。

## Week 2: プロンプト設計

### 2-1. 曖昧な指示 vs 具体的な指示（比較実験）
セッションAのプロンプト（曖昧）:
```
taskmanの検索機能を改善して。
```
セッションBのプロンプト（具体的）:
```
TaskService.search() を修正してください。
現状: `keyword in t.title or keyword in t.tags` のため、大文字小文字が区別され、
タグは完全一致しかヒットしません。docstringには「大文字小文字を区別しない」と書かれており、実装と仕様が食い違っています。
期待動作:
- タイトルは大文字小文字を無視した部分一致
- タグは大文字小文字を無視した部分一致（1つでも一致すればヒット）
制約: 依存パッケージを追加しない。変更は src/taskman/service.py と tests/ のみ。
完了条件: 上記3点を確認する新規テストを追加し、`pytest -q` と `ruff check .` がクリーン。
```
検証: 2つのPRの差分・所要時間・手戻り回数を比較してメモする。
学び: 「現状 / 期待 / 制約 / 完了条件」の4点セットが成功率を決める。

### 2-2. バグ修正（再現 → 修正 → テスト）
`docs/BUG_REPORTS.md` の BUG-1（ID重複）をそのまま貼り付けます。
プロンプト:
```
docs/BUG_REPORTS.md の BUG-1 を修正してください。
手順: (1) 失敗するテストで再現 → (2) 修正 → (3) テストがパスすることを確認。
完了条件: 再現テストを含め `pytest -q` 全件パス、`ruff check .` クリーン。修正方針をPR説明に書いてください。
```
検証: 再現テストが先に追加されているか、PRのコミット履歴で確認する。
学び: 「再現してから直す」と指示すると、修正の妥当性が検証可能になる。

### 2-3. 未実装機能の実装（インターフェースを与える）
プロンプト:
```
TaskService.summary() を実装してください（現在 NotImplementedError）。
戻り値の仕様:
{
  "total": int,      # 全タスク数
  "done": int,       # 完了数
  "open": int,       # 未完了数
  "overdue": int,    # 期限切れの未完了数（overdue() の定義に従う）
  "by_tag": dict,    # タグ -> そのタグを持つタスク数（タグなしは含めない）
}
あわせて CLI に `taskman summary` サブコマンドを追加し、1行1項目で出力してください。
完了条件: summary() のユニットテストを追加し `pytest -q` 全件パス、`ruff check .` クリーン。
```
検証: `taskman --file ./tasks.json summary`
学び: 出力仕様（型・キー）まで書くと、意図しない設計になりにくい。

### 2-4. タスク分解の練習
プロンプト:
```
「taskman に繰り返しタスク（毎日/毎週）機能を追加する」というタスクを、
Devinに1セッションずつ投げられる粒度に分解した実装計画を作ってください。
各ステップに「変更対象ファイル」「完了条件」を明記してください。実装はまだ行わないでください。
```
学び: 大きな機能は「計画セッション → 実装セッション」に分けると成功率が上がる。

## Week 3: 環境とコンテキストの整備

### 3-1. Blueprint（環境設定）の整備
プロンプト:
```
このリポジトリ用のDevin環境設定（blueprint）を整備してください。
- initialize: Python 3.11 と venv 作成
- maintenance: pip install -e ".[dev]"
- knowledge: lint コマンド `ruff check .` / test コマンド `pytest -q` / 実行 `taskman --help`
docs/blueprint.sample.yaml を参考に、read_environment_config で現状を確認してから提案してください。
```
検証: 次のセッション開始時に、依存インストール済みで即 `pytest` が走るか。
学び: 環境が整っていないと、Devinはセットアップに時間を使ってしまう。

### 3-2. Knowledgeの整備
プロンプト:
```
docs/knowledge.sample.md の内容をもとに、このリポジトリ用のナレッジノートを提案してください。
含める内容: ディレクトリ責務、コーディング規約（ruff設定に準拠、型ヒント必須）、
テストの書き方（tmp_pathフィクスチャを使う）、PRの粒度。
```
学び: 「毎回同じ説明をしている」ことはすべてKnowledge化する。

### 3-3. Playbookの作成
プロンプト:
```
docs/playbook.sample.md を参考に、「未カバーの関数にユニットテストを追加する」再利用可能なPlaybookを作成してください。
手順・完了条件・禁止事項（プロダクションコードは変更しない等）を明記してください。
```
学び: 反復タスクはPlaybook化して品質を固定する。

## Week 4: ワークフロー組み込みと並列化

### 4-1. Slack / チケット起点で依頼
Slackスレッドでメンションして依頼:
```
@Devin devin-practice の `taskman list` を、期限が近い順に並べる `--sort due` オプションに対応させて。
未指定時は今の優先度順のまま。テスト追加、pytest と ruff がグリーンになったらPRを出して。
```
学び: 議論の文脈がそのままDevinの入力になる。

### 4-2. 並列セッション（独立タスク3件を同時に）
それぞれ別セッションで:
```
A: overdue() の「当日は期限内として扱う」というdocstringと実装（due <= today）の食い違いを修正し、テストを追加してください。完了条件: pytest / ruff クリーン。
B: storage.py に保存の原子性（一時ファイルに書いてから置換）を実装し、テストを追加してください。完了条件: pytest / ruff クリーン。
C: CLI に `--json` オプションを追加し、list の結果をJSONで出力できるようにしてください。完了条件: pytest / ruff クリーン。
```
学び: 依存のないタスクは並列化するとスループットが上がる。レビュー側がボトルネックになる感覚もつかむ。

### 4-3. Automation（定期実行）
```
毎週月曜9時に、このリポジトリの依存関係を確認してアップデートPRを作るAutomationを設定してください。
テストがグリーンな場合のみPRを作成する方針にしてください。
```

### 4-4. 振り返り
```
このセッション群のうち、うまくいかなかったセッションを分析し、
原因（指示不足 / 文脈不足 / 環境不備 / タスク粒度）と、次回のための改善案をまとめてください。
```
