# Devin 学習プラン（4週間 / 実践重視）

参考: [Devin公式ドキュメント](https://docs.devin.ai) / [Devin入門](https://docs.devin.ai/get-started/devin-intro) / [効果的な指示の出し方](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)

## 全体の考え方
Devinは「新しくチームに入ったエンジニア」に近い存在です。したがって学習の本質は「ツールの操作を覚える」ことではなく、
1. **どのタスクを任せるか（タスク選定）**
2. **どう指示するか（プロンプト設計）**
3. **どう文脈を渡すか（Knowledge / Blueprint / Playbook）**
4. **どう検証するか（PR・CI・テスト）**
を身につけることです。上記4点を週ごとに積み上げます。

---

## Week 1: 基礎とセッションの回し方

### 学習項目
- Devinの得意・不得意（並列タスク、移行/リファクタ、反復作業、PRレビュー、コードベースQ&A）
- セッションの仕組み（VM、シェル、ブラウザ、ファイル編集、PR作成まで自律実行）
- Webアプリの画面: セッション一覧 / Browser（デスクトップ）タブ / Editor / PR
- セッションモード（Ultra / Fast / Lite など）とACU（消費単位）の感覚をつかむ

### 実習（小さく始める）
1. 既存リポジトリで **コードベースQ&A** を依頼する（コード変更なし）
   - 例: 「このリポジトリの認証処理の流れを説明して。関連ファイルを引用して」
2. **README / ドキュメント修正**のような低リスクな変更を1件依頼 → PRをレビューしてマージ
3. **ユニットテスト追加**を1件依頼（成功基準が明確なタスクの練習）

### 到達目標
- 1セッション = 1つの明確なタスク、という粒度感がわかる
- PRベースでDevinの成果物をレビューできる

---

## Week 2: プロンプト設計（最重要）

### 学習項目
- 良いプロンプトの構造:
  1. 目的（何をなぜ）
  2. 対象範囲（触ってよいファイル/触ってはいけない範囲）
  3. 実装方針（判断はこちらで決める）
  4. **完了条件**（テストが通る / CIがグリーン / この出力になる）
  5. 参考情報（既存の類似実装、ドキュメントURL、ログ、エラー全文）
- アンチパターン: 曖昧な要求、複数タスクの詰め込み、判断をDevinに委ねすぎる、検証不能なタスク
- タスクの分解方法（大きな機能 → インターフェース層 → 実装層 → テスト）

### 実習
1. 同じタスクを「曖昧な指示」と「詳細な指示」の2セッションで依頼し、結果を比較する
2. バグ修正を「再現 → 修正 → テスト追加」の完了条件付きで依頼
3. セッション途中で軌道修正するメッセージの練習（早めに介入するのが効果的）

### 到達目標
- タスク開始前チェックリスト（明確か / 検証可能か / スコープが閉じているか）を自分の言葉で書ける

---

## Week 3: 環境とコンテキストの整備（成功率を上げる仕組み）

### 学習項目
- **Blueprint（環境設定YAML）**
  - `initialize`（ランタイム・システムパッケージ、ビルド時のみ）
  - `maintenance`（依存関係の更新、セッション開始時に提示）
  - `knowledge`（lint / test / build コマンドの参照情報、非実行）
  - リポジトリ単位 と 組織単位 の使い分け
- **Knowledge（ナレッジ）**
  - 自動生成ノートのレビュー、pin（全リポジトリ / 特定リポジトリ）、トリガー説明の書き方
  - アーキテクチャ・規約・チームのワークフローはKnowledgeに寄せる
- **Playbook**
  - 繰り返しタスク用の再利用可能プロンプト。まずKnowledgeを整えてから作るのが推奨
- **Secrets**（一時利用 / 永続保存、最小権限のサービスアカウント）

### 実習
1. 自分の主要リポジトリのBlueprintを整備し、セットアップ〜テスト実行までDevinに検証させる
2. 自動生成Knowledgeを1〜2件レビュー・修正し、必要なものをpinする
3. 「テスト追加」「依存アップデート」など反復タスクのPlaybookを1つ作成し、実際に走らせる

### 到達目標
- 「同じ説明を2回した」ら Knowledge / Playbook / Blueprint に落とす習慣がつく

---

## Week 4: ワークフローへの組み込みと並列化

### 学習項目
- 連携先: Slack / Teams（スレッドでメンション）、Linear / Jira（チケットから起動）、GitHub（PRレビュー）、IDE拡張、Devin CLI（ターミナル）、API、MCP
- 並列運用: 複数セッションを同時に走らせる、子セッションでタスクを分割する
- Automations（スケジュール実行 / イベント駆動）
- セッションの振り返り（うまくいかなかったセッションの原因分析 → Knowledge化）

### 実習
1. Slack（またはTeams）連携を設定し、スレッドからDevinにタスクを依頼
2. チケット管理ツールから1件、チケット起点でPRまで到達させる
3. 独立した小タスクを3件同時に走らせ、レビュー負荷とスループットを体感する
4. 定期タスク（例: 依存関係の週次アップデートPR）をAutomationで1つ設定

### 到達目標
- 「朝タスクを切り出して投げ、レビュー待ちのPRを回収する」運用サイクルが回る

---

## 継続的に伸ばすためのルーチン
- 各セッション後に1分の振り返り: **うまくいったか / 原因は指示か文脈か / 何をKnowledgeに残すか**
- 週1回: Knowledge・Playbook・Blueprintの棚卸し
- 成功したプロンプトはテンプレとして保存し、Playbook化する
- 失敗パターンを記録する（Devinが苦手なのは、検証不能・仕様が曖昧・巨大リファクタ・実行環境が整っていないタスク）

## タスク難易度の目安（任せる順序）
| 難易度 | 例 |
|---|---|
| 易 | ドキュメント修正、コードベースQ&A、ユニットテスト追加、lint修正 |
| 中 | 明確なバグ修正、小規模機能追加、依存アップデート、PRレビュー対応 |
| 難 | 言語/フレームワーク移行、機能フラグ削除、新規機能のフルスタック実装 |
| 不向き | 仕様が未確定な設計判断、検証手段のないタスク、本番影響の大きい手動運用 |

## 学習用コードと実行方法
本プランの演習は、同梱の練習プロジェクト `devin-practice`（タスク管理CLI / Python）で行います。
- セットアップ・実行方法: `README.md`
- 週別の演習とコピペ用プロンプト: `docs/EXERCISES.md`
- Devinに渡すバグ報告サンプル: `docs/BUG_REPORTS.md`
- Blueprint / Knowledge / Playbook のサンプル: `docs/*.sample.*`

検証コマンド（Devinの成果物レビューに毎回使う）:
```bash
pytest -q && ruff check .
```
